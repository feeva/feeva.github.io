2026년 현재 어떤 데이터베이스가 좋은가?

이동련 · 2026. 11. 16.
프로그래밍
목차

2014년에 데이터베이스 SQL 특성 비교라는 글을 올렸다. 그때는 Oracle 10g니 SQL Server 2012니 등이 많이 사용될 땐데 SQL 구문이나 기능이 달라서 여러 데이터베이스에 익숙한 게 곧 경쟁력이었다. 페이지 조회 SQL 하나 짜려고 ROWNUM을 두 번 감싸던 시절이다.

그 뒤로 12년이 지났다. 내 경우 오라클을 안 쓴 지는 7~8년쯤 되고 PostgreSQL이 상용 프로젝트에서 일반화되는 걸 봤고 SQL Server는 상용 프로젝트에서 많이 안 보인다.

그럼 2026년 현재에 데이터베이스를 비교해보면 어떨까?

최근 OKKY에 "DB 머가 좋은가요"라는 질문이 올라왔다. PostgreSQL, MySQL, Oracle을 성능, 안정성, 개발 편의성, 비용으로 비교해 달라는 질문이었고 질문자는 MySQL의 프로시저와 커서가 너무 느리다고 했다. 마침 잘됐다 싶어 12년 만에 비교를 다시 해보기로 했다.

그동안 달라진 점

  • 설치: 예전엔 오라클 설치만 반나절을 낑낑대곤 했다. 지금은 도커 명령 한 줄이면 되고 그 한 줄도 AI가 쳐준다.
  • 운영: 클라우드 관리형 DB가 흔해졌고 작은 서비스라면 무료 티어로 충분하다.
  • 지식: DB마다 다른 SQL 구문, 즉 dialect(방언)는 AI가 알아서 맞춰준다. 날짜 처리 함수를 MySQL, Oracle에서 어떻게 하는지 외울 필요가 없다.

그래서 비교 기준은 얼마나 쉽게 띄우고 운영까지 일관되게 개발할 수 있는지, 프로젝트별로 필요한 기능이 잘 돼 있는지로 바꾸는 게 맞다.

비교 대상은 (내 기준으로는) 많이 사용되는 네 가지 선수다. 요즘 로컬 개발에서 다시 주목받는 SQLite, 대세가 된 PostgreSQL, 여전히 많이 쓰는 MySQL, 상용에서 많이 보이는 Oracle이다.

참고로 오라클은 이름에 AI가 붙어서 이번 버전의 이름이 Oracle AI Database 26ai Free였다. 오라클은 옛날부터 버전 뒤에 당시 유행하는 기술의 첫글자를 붙였는데(8i, 10g, 12c,…) 이번에도 오라클다운 작명 같다.

실험으로 몇 가지 비교해보자

말로만 하면 재미가 없으니 DB를 각각 실행해서 비교하기로 했다. 정확히는 Claude Code한테 시키고 나는 지켜봤다.

  • 장비: M4 맥, 메모리 16GB, Docker Desktop
  • 버전: SQLite 3.45, PostgreSQL 18.7, MySQL 8.4(LTS), Oracle AI Database 26ai Free
  • 설정: 전부 기본값. 튜닝은 하지 않았다.
  • 데이터: 개인적으로 만든 자료의 SQLite 백업. 테이블 8개가 있다.

SQLite는 파일 기반 데이터베이스라 연동 라이브러리만 있으면 되고 다른 데이터베이스는 도커로 실행했다.

1라운드: 띄우기

SQLite PostgreSQL MySQL Oracle
이미지 크기 없음 701MB 1.11GB 2.29GB
처음 띄우기 0초 1.1초 8.0초 10.6초
다시 켜기 0초 0.1초 0.9초 1.9초
대기 중 메모리 없음 26MB 약 450MB 약 2GB

역시 2020년대 기술은 옛날과 비교해 비약적이다. Oracle을 명령 하나만으로 10초에 띄울 수 있다니 말이다. 옛날에는 서버에 직접 붙어서 몇 기가 되는 설치 파일을 받고 OS 환경, Java 환경, Oracle 환경 등을 맞추고 설치 프로그램 실행하면서 여러 가지 선택하고 입력해야 했다.

그런데 메모리는 뭐지. PostgreSQL은 26MB로 엄청 가볍네. 몰랐는데 MySQL보다 훨씬 가볍구나! (그런데 AI가 메모리를 절대적인 수치로 보지 말라고 한다. 프로세스별 집계 방식이나 공유 메모리 포함 여부에 따라 달라질 수 있다고 한다.)

2라운드: 데이터 이전

데이터 백업을 SQLite에서 나머지 세 DB로 옮겨봤다. 처음엔 Claude한테 별 생각 없이 옮겨보라고 했다.

  • PostgreSQL: 한 번에 통과했다. 간단하군!
  • MySQL: 테이블은 만들어졌는데 인덱스 4개가 실패했다. MySQL은 TEXT 컬럼에 길이를 지정하지 않으면 인덱스를 만들어주지 않는다. 날짜를 문자열로 저장한 컬럼들을 VARCHAR(255)로 바꾸니 해결됐다.
  • Oracle: 4건이 실패했다.
    • 4,000바이트가 넘는 글이 VARCHAR2(4000)에 안 들어갔다. 그래서 CLOB으로 바꿨다.
    • 컬럼 이름 date가 예약어라 테이블을 만들 수 없었다. 식별자를 전부 따옴표로 감쌌더니, 이후로는 모든 쿼리에 따옴표를 붙여야 했다.
    • 마지막 문제는 빈 문자열 처리였다. 오라클에서 빈 문자열('')은 NULL이다. 값이 빈 컬럼이 딱 하나 있었는데 NOT NULL 컬럼이라 입력이 거부됐다.

2014년에 썼던 글대로 여전히 DB 간 특성이 달라 발생하는 문제들이었다. AI도 처음엔 모르니 오류를 보고 해결하면서 완료해야 했다.

Claude가 택배 기사라면 배달 장소에 따라 특성을 미리 몰랐던 건데 이런 건 스킬이나 하니스로 해결될 문제 같다.

3라운드: 무거운 데이터 작업

실제 데이터는 수천 건이라 너무 가벼웠다. 그래서 같은 스키마에 가짜 데이터를 채웠다. 2만 레코드짜리 테이블과 100만 건짜리 하위 테이블이 됐다. 내용은 무작위 글자로 채웠지만 실험용이니까.

첫 번째 작업은 두 테이블을 조인해서 그룹별 집계를 구하는 것이었다.

SQLite PostgreSQL MySQL Oracle
집계 시간 0.9초 0.06초 1.1~3.2초 0.05초

오라클과 PostgreSQL은 거의 비슷하게 빨랐다. MySQL은 실행 직후 첫 측정은 3초가 넘었고, 다시 재니 1.1초였다.

두 번째는 OKKY 질문과 관련된 실험이다. 2만 레코드의 상태 값을 하위 테이블의 최종 레코드 값으로 갱신하는 작업이었고 방식을 세 가지로 실행했다.

  • SQL 한 방: UPDATE ... FROM이나 MERGE로 한 문장에 처리
  • 프로시저 커서: DB 안에서 레코드 한 행씩 꺼내 조회하고 갱신
  • 앱에서 반복: 앱이 일일이 조회와 갱신 쿼리를 DB로 보냄. JPA에서 for문 돌리는 방식이다.
SQLite PostgreSQL MySQL Oracle
SQL 한 방 1.3초 1.2초 0.8초 0.4초
프로시저 커서 (프로시저 없음) 1.6초 2.9초 0.9초
앱에서 반복 0.9~1.3초 6.4초 5.8초 5.7초

(두 번씩 돌린 대략값이다.)

여기서 볼 게 세 가지 있다.

  1. MySQL 커서는 실제로 느리다. SQL 한 방보다 3.5배 느리다. OKKY 질문자가 느낀 게 맞다. 그런데 SQL 한 방으로는 MySQL이 2등이다.
  2. 오라클은 아직 쌩쌩하다. SQL 한 방에서도, 커서에서도 1등이다. PL/SQL의 원조답다. 역시 자본주의?
  3. SQLite에서는 반복문이 죄가 아니다. 다른 DB는 서버/클라이언트 방식이니 왕복 4만 번 트래픽으로 6초가 걸렸는데 SQLite는 같은 프로세스 안이라 빠르다. SQLite 공식 문서에도 작은 쿼리를 많이 날려도 효율적이라고 나와 있다.

하나 더. 위에서 본 성능은 개인적으로 간단히 테스트한 거니 절대적인 결과로 오해하지 말길. 캐싱, 트랜잭션, for문 처리 방식 등 다양한 변수로 다른 결과가 나올 수 있다.

조사 결과 아래 같은 판단이 섰다.

  • SQLite는 이제 장난감이 아니다. JSON이나 벡터 검색 확장도 있고 D1이나 Turso처럼 SQLite를 그대로 운영해주는 서비스도 생겼다. 하지만 쓰기는 한 번에 하나씩만 되므로 사용자가 동시에 몰려서 쓸 서비스라면 서버 DB로 이사하는 게 좋다.
  • PostgreSQL은 현재 가장 무난한 선택으로 보인다. 로컬에서 가볍고 무료로 운영할 곳이 많고 GIS부터 벡터 검색(pgvector)까지 확장이 넘친다. MySQL 쪽 관리형 서비스로 유명하던 PlanetScale이 2024년에 무료 플랜을 없애더니 이제 Postgres까지 판다. 시장이 PostgreSQL로 넘어가는 중이다.
  • MySQL은 여전히 좋다. SQL 한 방 성적도 좋았다. 다만 처리 로직을 DB 프로시저에 몰아넣고 오라클처럼 쓰면 기대한 결과가 나오지 않을 것 같다.
  • Oracle은 성능은 여전히 최상급이고 로컬에서 띄우는 것도 많이 쉬워졌다. 무료판은 CPU 2개, 메모리 2GB, 데이터 12GB까지라 공부나 개발용으로는 충분하다.

그럼 뭘 쓰지?

  • 혼자 쓰는 도구나 개인 프로젝트: SQLite. 서버를 띄울 필요가 없다.
  • 다중 사용자용 서비스: 지금은 PostgreSQL이 대세. 여러 면에서 무난하다.
  • 이미 MySQL이나 Oracle로 돌아가는 시스템: 그대로 쓰면 된다. 바꾸는 비용이 더 크다.

OKKY 질문에 답하자면 MySQL이 느린 게 아니라 커서가 느린 거다. DB를 바꾸기 전에 그 로직을 SQL 한 방으로 바꾸면 아마 꽤 빨라질 거다. 한 줄씩 처리하는 방식은 오라클 PL/SQL 패턴인 경우가 많은데 오라클은 그 방식에서도 빨랐기 때문에 MySQL과는 다르다.

2026년의 데이터베이스는 다른 개발 분야처럼 어렵게 넘어야 할 산이 아니다. 예전처럼 Oracle DBA가 넘사벽 엔지니어던 시절은 지났다. 좌충우돌은 하더라도 AI가 많이 알아서 해준다. 하지만 우리 개발자는 DB의 특성을 이해하고는 있어야 한다. 그런 면에서는 여전히 여러 DB를 경험해보고 공부하는 게 좋다.

오랜만에 오라클을 다시 만났지만 이제 컨테이너를 지워야겠다. 메모리 2GB, 디스크 2GB가 아깝다.
